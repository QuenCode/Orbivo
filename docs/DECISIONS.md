# Decisions

| Date | Decision | Reason |
|---|---|---|
| 2026-11-05 | Own development instead of an existing player | Existing solutions are consumer-oriented or (SightLab) too expensive and oversized; what is needed is pure operator control from outside |
| 2026-11-05 | C#/.NET instead of Unity or C++ | Experience with C#; full control; no engine license |
| 2026-11-05 | Spatial sound in the player, headphones without their own room simulation | Only the player knows the head orientation |
| 2026-11-05 | Project name "Orbivo" | Independent coinage; "Orbis" is already taken in the VR field |
| 2026-11-05 | Git: private repository `QuenCode/Orbivo`, work happens on `development`, `main` takes stable states. Commits with the private address (repository setting only) | Wish of the project owner |
| 2026-11-05 | Package versions (as of 2026-11-05, newest stable each): CommunityToolkit.Mvvm 8.4.2, Microsoft.Extensions.Logging 10.0.14, Silk.NET.OpenXR 2.23.0, Vortice 3.8.3, FFmpeg.AutoGen 9.0.1.1, NAudio.Wasapi 3.3.0, xunit.v3 4.0.2; SDK 10.0.401 (`latestPatch`) | Pinned centrally in `Directory.Packages.props` |
| 2026-11-05 | NAudio 3.3.0 instead of 2.4.0 | The span-based `Read` API fits the allocation-free audio callback. NAudio 3 is young (since 08/2026); falling back to 2.4.0 only affects `Orbivo.Audio` |
| 2026-11-05 | Tests with xUnit v3 4.x on Microsoft.Testing.Platform (`global.json` → `test.runner`), without `Microsoft.NET.Test.Sdk` | xUnit 4 no longer supports VSTest on the .NET 10 SDK in the default package. Every test project needs at least one test, otherwise the run ends with an error |
| 2026-11-05 | FFmpeg 9.0.2 as LGPL shared build from BtbN (month-end build `autobuild-2026-10-31-12-59`), license **LGPL v3 or later** | gyan.dev offers shared builds only under the GPL. BtbN builds with `--enable-version3`; LGPL v3 is compatible with N5. Month-end builds stay available for two years. The app rejects non-LGPL builds at startup (replaced on 2026-11-11 by an own build) |
| 2026-11-05 | Steam Audio 4.8.1; only `phonon.dll` is shipped | `TrueAudioNext.dll`/`GPUUtilities.dll` only serve convolution on AMD GPUs. The P/Invoke is written exactly against 4.8.1; the app checks the file version |
| 2026-11-05 | Native DLLs via `native/fetch-native.ps1` (pinned URLs + SHA256), not in Git; the build stays green if they are missing | Reproducible, the repository stays small; the app reports missing DLLs in the status |
| 2026-11-05 | Project dependencies: Core ← Media, Audio; Xr → Core, Media; App → all. Xr creates the D3D11 device and passes it to Media. Lock-free structures shared by two projects (audio ring buffer, head pose snapshot) live in Core | The renderer reads the GPU frames from Media; Core stays free of native dependencies |
| 2026-11-05 | Exception to rule 5: only the software decoder fallback may upload frames from the CPU to the GPU, with a warning in the status | F40 provides for software decoding; without an upload that would not work. Hardware decoding stays the normal case; 8K in software is not real-time capable |
| 2026-11-05 | The sidecar is called `<file name with extension>.orbivo.json`, e.g. `clip.mp4.orbivo.json` | No collision between `clip.mp4` and `clip.mkv` |
| 2026-11-05 | The solution stays in the `.sln` format (not `.slnx`, the default since .NET 10) | The commands in CLAUDE.md use `Orbivo.sln` |
| 2026-11-05 | NuGet audit warnings NU1901–NU1904 do not become errors | New security advisories should be visible but not break the build overnight |
| 2026-11-05 | Own file logger for Microsoft.Extensions.Logging (bounded queue, writer task, drops on overflow instead of blocking) instead of Serilog | No extra dependency. Render thread and audio callback still do not log per frame/buffer, because formatting allocates |
| 2026-11-05 | Test media: "8K" = 8192 px wide; top-bottom 8192×8192; 360° side-by-side with horizontally squeezed eyes (8192×4096) | Hardware decoders end at 8192 px; the full SBS width (16384) could not be decoded |
| 2026-11-05 | Yaw sign everywhere: rotation about +Y by the right-hand rule, **positive = left**. Equirect: picture center = front, left in the picture = left | Follows directly from the OpenXR convention; the Ambisonics azimuth is then identical to yaw. Also applies to the orientation offset in the sidecar (F14) |
| 2026-11-05 | Ambisonics chain for Steam Audio: FuMa → AmbiX (SN3D) → N3D (`iplAudioBufferConvertAmbisonics`) | Steam Audio computes internally in N3D (`phonon.h`). Steam Audio uses the same coordinate system as OpenXR; the conversion only concerns the Ambisonics axes (X forward, Y left, Z up) |
| 2026-11-05 | M1: folder and namespace `Orbivo.Core.Geometry` instead of `Math` | A namespace `Orbivo.Core.Math` would hide `System.Math` in all `Orbivo.Core.*` namespaces |
| 2026-11-05 | M1: viewing direction per pixel from three vectors (`ViewRayBasis`: `dir = normalize(ndc.x·R + ndc.y·U + C)`) instead of a 4×4 matrix | Mathematically the same as `invViewRotProj`. C# and HLSL need not agree on a row/column layout, a typical source of mirroring |
| 2026-11-05 | M1: **Gamma** – sRGB views throughout. Image texture `B8G8R8A8_UNORM_SRGB`, the shader computes and writes linear. Desktop: swapchain `B8G8R8A8_UNORM` with RTV `B8G8R8A8_UNORM_SRGB` (the flip model allows no sRGB swapchain format). Headset from M2: swapchain `R8G8B8A8_UNORM_SRGB`. From M3 the shader linearizes the video after YUV→RGB | OpenXR runtimes treat non-sRGB formats as linear; the picture would be too bright. Filtering thus happens in linear light. A test checks that the colors of the test image arrive unchanged |
| 2026-11-05 | M1: shaders as embedded resources, compiled at startup with `d3dcompiler_47.dll` (part of Windows), warnings count as errors | No Windows SDK needed on build machines. Errors appear in the log at startup; a unit test compiles all entry points |
| 2026-11-05 | M1: no mipmaps, `SampleLevel 0`, U wrapping, V clamped | Video textures have no mipmaps anyway. Without mip selection there is no seam at ±180°. The headset magnifies rather than minifies; the preview window flickers a little at a wide field of view |
| 2026-11-05 | M1: preview window (`--no-xr`) as an own Win32 window on its own render thread, without a close button. Flip model swapchain with frame latency handle (max. 1 frame), VSync | Replaces the headset: the operator window looks the same in both modes, rendering and mouse do not go through the UI thread, and the loop is built like the XR loop |
| 2026-11-05 | M1: the mouse grabs the picture (like YouTube 360 and Street View): drag to the right = look to the left. Mouse wheel = vertical field of view 30–120°, start 75°, Home = reset | Usual on the desktop. Reversing it would be one sign in `MouseViewSource` |
| 2026-11-05 | M1: still images via WIC through WPF in `Orbivo.App`, no new package. Decoding and texture creation on a worker thread, handover via `Interlocked.Exchange` | Vortice.WIC would be an extra package. The render thread does no I/O |
| 2026-11-05 | M1: D3D11 device on the most powerful GPU (`EnumAdapterByGpuPreference`), with `VIDEO_SUPPORT` and `SetMultithreadProtected(true)`; debug layer in the debug build if installed (Windows feature "Graphics Tools", present on the development computer since 2026-11-05). Release builds never request it; the target PCs do not need the Graphics Tools | Laptops also have an integrated GPU. `VIDEO_SUPPORT` is needed for D3D11VA in M3. From M2 OpenXR determines the adapter (LUID). Messages of the debug layer appear in the debugger's output window, not in the log |
| 2026-11-05 | M1: new test project `Orbivo.Xr.Tests`. Tests run on WARP (the software rasterizer of Windows); WPF only for reading and writing PNG | Rule 8 is checked automatically: shader and `ProjectionMath` are compared pixel by pixel. The direction test with the test image is skipped if the test media are missing. The rendered views end up under `tests/Orbivo.Xr.Tests/bin/…/rendered-views/` |
| 2026-11-05 | M2: OpenXR loader 1.1.65 from the Khronos release `openxr_loader_windows-1.1.65.zip` (Apache-2.0), via `fetch-native.ps1` with pinned URL and SHA256. Plus `hello_xr.exe` and `openxr_runtime_list.exe` as diagnostic tools (not in the app output). Orbivo requests OpenXR 1.0 | Silk.NET.OpenXR contains no loader. Same route as FFmpeg and Steam Audio; the NuGet package `OpenXR.Loader` is built for C++ projects. 1.0 covers everything Orbivo needs and runs on every runtime |
| 2026-11-05 | M2: `XrHost` with its own XR render thread (priority "Highest"), built like the preview window. If runtime or headset are missing, it retries every 2 s; the instance stays and only `xrGetSystem` is repeated (recommendation of the OpenXR specification). Unexpected errors: a new attempt after 2 s, then twice as long up to at most 30 s. Every state is logged only once | N3: the app keeps running, the operator sees the reason in the status. Pauses only happen outside the frame loop; inside it only `xrWaitFrame`/`xrWaitSwapchainImage` block (frame pacing of the headset) |
| 2026-11-05 | M2: the D3D11 device is created at the first connection on the adapter OpenXR specifies by LUID (`GraphicsDevice.CreateOnAdapter`) and lives until the app ends. If the headset later requires another GPU, the status reports an error; Orbivo must then be restarted | Textures and from M3 the decoder depend on the device. A GPU change at runtime practically never happens |
| 2026-11-05 | M2: one swapchain per eye in the recommended size. Format `R8G8B8A8_UNORM_SRGB`, otherwise `B8G8R8A8_UNORM_SRGB`, never a linear format (the start then fails with an error). RTVs with explicit format, created in advance for all swapchain images | Gamma decision from M1. Runtimes may create the textures "typeless". RTVs created in advance keep the frame loop allocation-free |
| 2026-11-05 | M2: reference space `LOCAL`, projection `PRIMARY_STEREO`, one projection layer, blend mode `OPAQUE`. Rendering uses only the orientation of each eye; the layer carries the measured pose (with position) so that the compositor reprojects correctly. If the orientation is invalid in a frame, the last valid views are reused; before the first valid one the headset stays black | Rule 6. With content at infinity the position changes nothing in the picture. A short tracking loss should not flash black. Quad views (Varjo focus/context) are a later optimization |
| 2026-11-05 | M2: lifecycle as an own, testable state machine (`XrSessionLifecycle`): `READY` → `xrBeginSession`, `STOPPING` → `xrEndSession`. If the runtime ends or loses the session (`EXITING`, `LOSS_PENDING`), Orbivo rebuilds it after 2 s. When the app closes: `xrRequestExitSession`, wait at most 2 s, then destroy | Varjo Base can stop and restart a session. The operator window decides when Orbivo ends, not the runtime |
| 2026-11-05 | M2: `--image` now also works for the headset. The picture appears as soon as it is loaded. The start state "black" with release by the operator (F6) comes in M4. In headset mode there is no preview window (mirror preview F42 later) | M2 needs the test image in the headset; transport control only comes in M4 |
| 2026-11-05 | M2: status display in headset mode: headset (runtime name and version, headset name, resolution per eye), session state, frame output (fps and refresh rate of the headset, warning below 95 %), GPU, picture, viewing direction of the viewer (F41, average of both eyes) | F40/F41 |
| 2026-11-05 | M2: observed on the development computer without a connected headset: Varjo OpenXR Runtime 4.14.2 creates the instance and reports `XR_ERROR_FORM_FACTOR_UNAVAILABLE` | The case "Varjo Base installed, headset missing" is thus tested without a headset |
| 2026-11-06 | M2: headset test passed (all 8 points of the checklist): orientation, stable picture without moving along with head shifts, no double images, roll, no seam, colors, reconnecting after taking the headset off and after restarting Varjo Base, clean exit | Feedback of the project owner with a Varjo XR-3 |
| 2026-11-06 | M3: FFmpeg decodes via D3D11VA on the shared device (`av_hwdevice_ctx_alloc`, `AVD3D11VADeviceContext.device` = our device). `get_format` only accepts `AV_PIX_FMT_D3D11`. The first FFmpeg decoder with a D3D11VA hardware configuration is chosen, not the default decoder of the codec | Otherwise FFmpeg takes libdav1d (software) for AV1. If a hardware decoder is missing, the status reports "There is no hardware decoder for the codec …" |
| 2026-11-06 | M3: **hardware decoding only** for now. The software fallback (F40, exception to rule 5) follows later | 8K does not run in real time in software. The fallback is meant for smaller files and not needed for M3 |
| 2026-11-06 | M3: the decode thread copies every frame via `CopySubresourceRegion` on the shared immediate context into an own ring of 6 NV12/P010 textures. The D3D11 multithread lock protects the context | The order on the GPU is then automatically right: the copy comes before every later draw that reads the slot. The lock is only held while recording the copy command (microseconds), so the render thread waits at most that long. This is a deliberate, small deviation from rule 1. Alternatives would be a deferred context or fences (D3D11.4); only tackle them if measurements in the headset show stutter |
| 2026-11-06 | M3: 6 frame slots. One 8192×8192 NV12 frame takes 96 MiB, the ring about 576 MiB of graphics memory. Playback starts once 4 frames are ready | A buffer of about 200 ms at 30 fps; enough because the decoder (RTX 3070) is twice as fast as real time. More slots cost a lot of graphics memory |
| 2026-11-06 | M3: demux and video decode run on **one** thread for now (unlike the thread table in ARCHITECTURE.md). Separate threads come in M5 with the audio stream | Without audio there is nothing to distribute; one thread is simpler and keeps the decoder busy |
| 2026-11-06 | M3: handover decoder → render thread lock-free through `FramePacer` (two SPSC queues: free and ready slots). The render thread picks the newest frame with pts ≤ target time and counts skipped frames as "dropped". Swapping the frame queue on open and stop goes through a hazard pointer: the control thread releases an old queue only once the render thread no longer holds it | Rule 1. No lock between render and control thread |
| 2026-11-06 | M3: even when nothing is drawn (headset reports `shouldRender = false`, no session, preview minimized), the render thread collects due frames. Without a session every 50 ms | Otherwise the decoder stalls with a full ring while the clock keeps running, and the video would afterwards have to catch up by dropping. Found by a test without a render loop |
| 2026-11-06 | M3: until the audio clock (M5) playback follows `SystemPlaybackClock` (stopwatch/QPC). In the headset the frame is chosen for the predicted display time: `XR_KHR_win32_convert_performance_counter_time` converts it into a QPC timestamp. Without the extension "now" applies (warning in the log) | Same time base as the system clock. The preview shows with one frame of latency and takes "now" |
| 2026-11-06 | M3: playback states: no video → opening → ready (headset black until Play, F6) → playing ⇄ paused (picture stands still, head tracking continues) → end (last picture stays). **Stop** = restart the decoder, headset black, position 0. Play after the end plays from the start. State machine `PlaybackStateMachine` in Core, with unit tests | F6. For the operator Stop means "back to the start, the viewer sees nothing" |
| 2026-11-06 | M3: **video gamma** (open point from M1) decided provisionally: after YUV→R′G′B′ the shader linearizes with the sRGB curve. Through the sRGB render target the code values of the video arrive unchanged, as in usual players | Matches what creators see on their monitor. A test compares the shader with the C# reference `VideoColor` |
| 2026-11-06 | M3: YUV matrix BT.601/709/2020 and limited/full range from the stream; if the information is missing, BT.709 from 720 lines up and limited range apply. BT.2020 material is converted in linear light to BT.709 primaries (without gamut mapping, values outside are clipped). 10 bit (P010) is supported | The headset shows sRGB/BT.709. HDR curves (PQ/HLG) are not evaluated yet, see open points |
| 2026-11-06 | M3: stereo layout (mono/TB/SBS) brought forward from M6, because the headset test requires an 8K TB video. Without information: square = top-bottom, otherwise mono. `--stereo mono|tb|sbs` overrides it. Top or left is the left eye. At the border of the half pictures sampling is clamped to half a texel so that the other eye does not bleed through. The sidecar (M6) replaces the guessing | `ProjectionMath.CreateEyeSourceRect`/`SourceUv` and `projection.hlsl` with a pixel-by-pixel comparison test (rule 8) |
| 2026-11-06 | M3: new start option `--video <path>` loads a video at startup (the operator presses Play). Play/pause/stop in the operator window, commands through `Channel<PlayerCommand>` | Until file selection arrives in M4 |
| 2026-11-06 | M3: the "Decoder" status shows decoded fps (over one second of wall time), buffer fill and dropped frames. | 2026-11-06 | M3: new test project `Orbivo.Media.Tests` with a real GPU and FFmpeg (skips itself without GPU, DLLs or test media). The tests run one after another in one collection, because they measure throughput and timing on the one video decoder of the GPU. Measured on the RTX 3070: 8K TB HEVC at 61 fps | Decoder, player flow and error messages are checked automatically without a headset |
| 2026-11-06 | M3: finding: Vortice hands out **one** shared `ImmediateContext` wrapper per device. Only the owner of the device (`GraphicsDevice`) releases it, all others borrow it | A `Dispose` in the player had invalidated the context for everyone else |

| 2026-11-06 | M3: headset test passed (all 10 points of the checklist): 8K TB video without stutter, frame output in step with the headset, buffer full and no dropped frames, stereo depth right (top = left eye), pause holds the picture with head tracking, stop black and back to the start, playback continues after taking the headset off, the end holds the last picture, clean exit | Feedback of the project owner with a Varjo XR-3 |
| 2026-11-06 | M4: **seek in the running decoder** instead of reopening. The decode thread handles the request itself: new frame generation in the `FramePacer`, `av_seek_frame` (keyframe before), `avcodec_flush_buffers`, decode forward. Frames ending before the target are dropped without a copy; the first published frame is the one at the target. If the target lies behind the last frame, the last frame is shown. Seeks in quick succession replace each other (only the last target counts) | No second frame ring in graphics memory (8K: 576 MiB), no rebuild of the hardware decoder. Measured on the RTX 3070: 4K about 30–60 ms, 8K TB 125–560 ms until 4 frames are ready |
| 2026-11-06 | M4: frame generations in the `FramePacer`: the render thread returns slots of older generations lock-free but keeps showing its current frame until a frame of the new generation is due. If the video is hidden (ready), `DiscardStaleFrames` clears the old slots anyway | During the seek the headset holds the last picture instead of flashing black (ARCHITECTURE.md had left "last picture or black" open). | 2026-11-06 | M4: the decode thread no longer ends at the end of the file but waits for a seek or the end of the decoder | Seek after the end and loop need no new decoder |
| 2026-11-06 | M4: a seek target that lies at most **1 ms** before the start of a frame counts as that frame | 30 fps is not a whole number of ticks: after three single-frame steps the target lay 1 tick before the frame and showed the previous one. Matroska stores times in ms (up to 0.5 ms deviation). Seek thus hits exactly the frame in all tests (done criterion ±1 frame) |
| 2026-11-06 | M4: seek per state: ready stays black (Play starts at the target), playing and paused stay (the clock stands until the seek is done), end becomes paused at the target. | 2026-11-06 | M4: **loop** (F3) in the player: at the end it seeks to 0 and plays on. In between the last picture stands briefly (the duration of a seek) | Simple and robust. Seamless would be decoding on with a time offset; only tackle it if the hitch disturbs in the headset |

Headset and preview fetch the factor per frame through `IVideoFrameSource.GetOutputBrightness` (lock-free, allocation-free). Default duration 1 s, adjustable 0.1–30 s | Linear in linear light looked like a jump at the dark end. | 2026-11-06 | M4: start state (F6): the headset stays black until the operator presses Play. Blackout is off at startup. `--image` stays a test tool and appears at once | Decision of the project owner |

| 2026-11-06 | M5: **audio clock** (rule 4): `AudioClockTracker` follows the device position with a PI controller (correction and drift estimate); errors above 30 ms reset the clock. | 2026-11-06 | M5: **no clicks:** play, pause, seek and stop fade the sound in or out in 5 ms (smoothstep). Volume, mute and blackout go through a smoother with a 5 ms time constant. | 2026-11-06 | M5: **volume curve** `level³` (50 % ≈ −18 dB), the same curve for fade. ## Open points

- **Sharpness of `PRIMARY_STEREO` on the XR-3:** without quad views Varjo does not fully use the focus display. Judge
  with real 8K material (from M3) whether quad views (`XR_VARJO_quad_views`) have to be brought forward.
- **FuMa second and third order:** rare and inconsistently defined. Only implement if real material requires it.
- **Real Ambisonics material in the listening test (M10):** the format is clear (AmbiX with `SA3D`, see 2026-11-09).
  Open is the listening test in the headset: direction matches the picture, loudness compared to stereo.
- **Real recording format** (SPEC, open points): one file is known (2026-11-09): 5760 × 2880 HEVC mono, 59.94 fps,
  first-order Ambisonics. 5.7K at 60 fps needs about a quarter of the pixel rate of 8K TB at 60 fps; check on the
  headset computer with the real video that "Decoder" reports no dropouts. Whether further recordings are 8K or
  stereo is open.
- **Video gamma:** provisionally the sRGB curve in M3. Check with real material in the headset whether BT.1886 looks
  more natural (dark areas).
- **HDR material (PQ/HLG):** the transfer curve of the stream is not evaluated yet; HDR video would look flat. Only
  needed if the real recording format is HDR. Then tone mapping in the shader and in `VideoColor`.
- **Software decoder with real material:** tested with H.264 Constrained Baseline 4320 × 2160 and HEVC. Check with the
  project owner's 60 fps video (H.264 High 4320 × 2160) whether the CPU keeps up; otherwise a hint in the status is
  enough.
- **Copy lock on the immediate context:** if stutter appears in the headset while copying the frames, switch to a
  deferred context or D3D11.4 fences.
- **DPI of the preview window:** the app does not scale per monitor. On a second monitor with a different scaling the
  preview can look blurry. Only tackle it if it disturbs.
- **Loop hitch:** at the end of a loop the last picture stands for the duration of a seek (8K about 0.1–0.5 s). Not
  disturbing in the M4 headset test; seamless would work with decoding on with a time offset, if real material
  requires it.
- **Keyboard shortcuts in the preview window:** if the preview window (`--no-xr`) has the focus, the shortcuts do not
  work. Only relevant for development.
- **Stop reopens the file:** stop still uses the decoder restart from M3. With the seek from M4 it would be faster
  (seek to 0 and black); only change it if it disturbs.
- **Error in the sound decoder during playback:** the video keeps running without sound; the error is only in the
  log, not as a warning in the status. Add it as a warning in the status when convenient (not done in M9).
- **Allocations in the release build (M9):** under load the allocation tests of the sound path occasionally report a
  few KB in the release build. Probably once when hot methods are recompiled (tiered compilation), not in every
  period. Check it, e.g. with `[MethodImpl(MethodImplOptions.AggressiveOptimization)]` on the methods of the audio
  period or with `TieredPGO` off, and then also run the tests in the release build.
- **`SnapshotCellTests.ConcurrentReads_NeverSeeATornValue` (M9):** failed once in the trial run of the release script
  (message not captured), afterwards not again in 5 full runs and 22 single runs. If it happens again, save the
  message: "values went backwards" or an unequal pair would be a bug in `SnapshotCell` (head direction and audio
  clock), "the writer was running" only a too tightly measured test.
- **Code signing (M9):** `Orbivo.exe` is not signed; Windows SmartScreen warns at the first start (the manual
  describes it). For distribution outside the project consider a code signing certificate.
- **Click on a device change:** the old stream ends hard (see the M5 decision). Only tackle it if it disturbs in
  operation.
- **Switching a monitor during playback:** if a monitor is switched off or on by hand (or replugged), video decoding
  stalls for a few seconds. Check with the XR-3 and the target PC (RTX 5080) in the headset test; if it happens there
  too, narrow down the cause in the driver/D3D11 (decoding or copy into the frame ring).
- **Surround (later):** since M10 ring buffer and block processing carry up to 16 channels. 5.1/7.1 then need virtual
  speakers (binaural effect per channel) and a loudness measurement as in M7.
- **Load of the Ambisonics stage (M10):** third order is more expensive than stereo. Check in the operator window
  ("Audio output", peak load) on the headset computer; above 50 % would be a reason to adapt the decoder order to the
  material.
- **Latency head → sound (F25, M7):** about 50 ms instead of ≤ 30 ms; almost all of it is the WASAPI output latency
  (shared mode, 20 ms buffer, measured 43 ms). Not noticed in the headset test with the stereo direction test
  (2026-11-08). If it disturbs with real material: predict the head direction by the measured latency (OpenXR delivers
  poses for a time in the future, `xrLocateViews` with a later time), or a smaller device buffer or exclusive mode.
- **Stereo width and sound with real material (M7):** check the default of 75° with real material in a listening test;
  the loudness (factor 0.6) is measured with noise, not with music or speech.
- **Lip sync with a real device:** WASAPI measures the latency of the output device itself. Windows does not always
  report Bluetooth or USB devices with extra internal latency correctly; check with the headphones actually used
  (headset checklist M5).
- **Decoding performance (N1):** 8K TB HEVC decodes on the RTX 3070 (development computer) with the copy into the
  frame ring at about 61 fps (`Orbivo.Media.Tests`, synthetic material), i.e. twice as fast as 30 fps material. For
  60 fps 8K TB that is just not enough. Measure on the RTX 4080 laptop and the RTX 5080
  (`dotnet test --project tests/Orbivo.Media.Tests`, output of the benchmark), then with real material.
- **EAC with real material (M6):** projection and layout are checked against ffmpeg `v360`, not against a real
  YouTube video. As far as we know, YouTube marks EAC with an `mshp` box (mesh) that FFmpeg does not report as a
  projection; such files appear as "no metadata" and need "EAC" in the operator window. Check with real material,
  possibly detect `mshp` ourselves.
- **Base orientation `prhd` (M6):** only shown. Decide with real material whether it should serve as a default for the
  offset.
- **Further formats (M6):** equirect crops other than VR180, stereo as frame sequence/rows/columns, rectilinear and
  "parametric immersive" projection (Apple) are only reported with a hint. Only implement when real material
  requires it.
- **Language change without restart (M11):** deliberately not implemented. If operators want to switch in the middle
  of a session, all texts would have to run through bindings to an exchangeable source.
- **Check English texts in the window (M11):** English texts are partly longer; check the window in both languages
  for cut-off labels (headset checklist M11).
- **Cubemap from `cbmp` (M6):** Spherical Video V2 only knows layout 0; we assume 3×2 (`rludfb`) for it, like YouTube
  and `v360`. Check with real cubemap material.
